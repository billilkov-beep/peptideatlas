01 / HOW IT WORKS

A connection for every website.

Register each website in the central workspace. Give it an individual key and choose the published categories it should receive. The connector handles delivery while the shared viewer keeps the human consistent.

The complete collection is populated on first start: 147 maintained profiles cover all 152 audited reference entries. Connected sites receive the full articles, fact tables, section citations, applicable FAQs, source tabs, and related profiles. All sites share the same published content while keeping their own design.

02 / WORDPRESS

Install once. Configure each site.

The same plugin ZIP works across your WordPress websites. Each installation receives its own connection key, content scope, and local branding settings.

  1. Open Connections → Connect a website. Choose WordPress, enter the website's domain, and select categories. An empty category selection means all published profiles.
  2. Copy the new key and download the connector below.
  3. In WordPress, open Plugins → Add New → Upload Plugin. Upload the ZIP and activate it.
  4. Open Settings → Peptide Atlas. Enter this application's HTTPS base URL and the connection key, then choose Save and synchronize.
  5. Add [peptide_atlas] to the WordPress page where the explorer should appear.

03 / OTHER PLATFORMS

A working Node.js example.

The project includes Forma Research, a complete example under examples/brand-site. It has a different visual identity, the same human component, and a server-held connection key.

  1. Create a JavaScript connection in the central workspace.
  2. Build the project with npm run build.
  3. Provide the central address and key through a private environment file or the hosting secret configuration.
  4. Start the example server from the project root.
# Private environment file — replace these placeholders.
ATLAS_URL=https://atlas.your-domain.example
ATLAS_NODE_KEY=YOUR_PRIVATE_CONNECTION_KEY
BRAND_PORT=3100
BRAND_HOST=127.0.0.1
node --env-file=/private/forma.env examples/brand-site/server.mjs

The example listens on port 3100 by default. Its browser reads the example's own /catalog route, while its server obtains the central snapshot. Profile pages are served at /peptides/<slug>.

SERVER-TO-SERVER INTERFACE

The published snapshot endpoint

GET /api/v1/node/snapshot
Authorization: Bearer YOUR_PRIVATE_CONNECTION_KEY

A snapshot includes the website's allowed published records, version, generation time, and expiry. The supplied adapter validates it and retains a bounded delivery copy. Other frameworks can reuse this pattern.

Local development: the Node example permits HTTP loopback only when ATLAS_ALLOW_LOCAL=true is explicitly set. WordPress has separate development-only constants documented in docs/CONNECTORS.md. Use HTTPS for production connections.

05 / UPDATES & AVAILABILITY

Keep delivery copies current.

Publishing updates the central snapshot. Connected websites retrieve that snapshot on their next successful synchronization.

SituationConnector behaviour
WordPress refreshEvery 15 minutes through WP-Cron; this depends on site traffic. Use a real scheduler for dependable low-traffic refresh.
Node example refreshEvery five minutes while the example process is running.
Successful updateThe local snapshot is replaced completely. Withdrawn and out-of-scope entries disappear.
Temporary network failureThe last valid copy remains available until its original expiry.
Expired snapshotContent becomes unavailable. Restarting the connector does not extend the expiry.
Rejected keyA 401 or 403 synchronization response clears the local snapshot.

Snapshot age is capped at 24 hours, or a shorter period specified centrally. Disabling a connection takes effect when that website next synchronizes; it cannot remove content a visitor has already downloaded.

  • Check the connection's Last synchronized time.
  • Test a published change and a withdrawal on a pilot site.
  • Confirm scheduled refreshes and full-page cache exclusions.
  • Compare the viewer on desktop, mobile, and a WebGL fallback device.
06 / FUTURE MILLIGRAM INTEGRATION

Keep the knowledge portable.

This application runs independently now. Each profile has a stable ID, and the workspace can export the drafts, published content, source references, revision history, and website configurations.

When Milligram is ready, map its existing data first, transfer and verify the library, then point the connectors to the chosen authoritative service. Avoid two independently editable copies during the transition.

Credentials stay separate. Portable exports exclude passwords, sessions, and connection keys. Imported website connections begin disabled and need new keys before use.

The supplied import/export format is implemented. A Milligram-specific importer depends on Milligram's actual schema and will be built when that integration begins. See docs/MIGRATION.md in the source package for the full cutover plan.

Start with two different websites.

Connect two pilot sites with clearly different styling. Verify a published update reaches both while the human model stays consistent, then roll out the same connector to the remaining sites.
